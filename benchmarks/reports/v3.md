## E8 — Dynamic output request boundaries (2026-10-11)

Before routing changes output allocations, check each request's output cap and thinking budget. V2's `maxTokens || config.maxOutputTokens` silently ignores an explicit zero; manual thinking uses the global maxOutputTokens even after the request cap is lowered, and permits budget_tokens equal to max_tokens. Overrides can also exceed the configured output ceiling.

The candidate validates the explicit override and configured ceiling, derives the manual thinking budget from the current request, and blocks too-small manual thinking limits before HTTP or cost reservation. Adaptive defaults stay unchanged. For the ordinary manual mode (this adapter sends no interleaved-thinking beta header), the minimum is 1,024 and the budget must be below max_tokens; see [Anthropic's primary documentation](https://platform.claude.com/docs/en/build-with-claude/extended-thinking). This local rule does not verify PackyAPI/GLM bridge compatibility or support of each thinking mode.

## E9 — Bidirectional policy simulation

The standalone candidate `src/policy.mjs` is implemented and remains separate from live `runTask`. The pure API is `createPolicyState({strategy, initialEffort})` and `decideEffort(state, observation, config)`. It observes assumed trusted runtime source identities and actual-tool-output shapes rather than assistant confidence, handles up/down/hold and budget stop, and creates no retry, test or model request.

Two distinct, aligned successful validation attempts on current source are needed for a downgrade; two failures on the same source and command for an upgrade. At least two observation steps must be held per setting. Zero tests, Git/help/search, unknown output, duplicate attempts, assistant success claims and pending validation cannot count as fresh success. Edits expire all previously declared attempts; source changes expire the prior snapshot's attempts while permitting a genuinely new validation from the same turn. Review found that an old attempt could revive after source identity returned; the watermark fix and four regression tests now cover this case.

`v3-policy-replay-verified` and independent root reproduction `v3-policy-root-20261011` run **13 fixed declared trajectories × 4 strategies = 240 observed steps**. Decisions, manifest and source snapshots match exactly between runs; source remains unchanged and inputs are not mutated.

- fixed-strong: low/high/max 0/0/60; no switches; two budget stops.
- fixed-weak: low/high/max 60/0/0; no switches; one budget stop.
- upgrade-only: low/high/max 21/3/36; three upgrades, no downgrade; one budget stop.
- bidirectional: low/high/max 22/11/27; four upgrades, five downgrades; one budget stop.
- Immediate reversal, minimum-hold violation, downgrade-evidence violation, budget violation and manufactured call counts: **all zero**.

The stop step is included in observed effort counts; allowed-request decisions are separately 58/59/59/59. No actual request was performed. Reservations are arbitrary abstract simulation units, with no Token/USD mapping, and declining a request preserves validation capacity rather than claiming validation completed. Protection counts inspect configured policy invariants and returned decisions; they do not establish real task quality.
