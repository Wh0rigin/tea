# 优先级 2：检索进展反馈实测

结论：这版不启用。代码直接基于正式版本 a3571e5，未包含优先级 1、PR24 提示词或额外固定复核轮次。保留 PR16 全套数值配置，仅增加默认关闭的检索重复提示。

## 实现与测试

对结构化检索请求和实际返回文本做哈希，仅记录最多 64 组摘要。连续三次重复已见请求/结果时，在完整工具输出后附加提醒；每轮最多两次，至少间隔十二次检索。新结果、非检索操作、错误和压缩检查点会打断重复判断。不跳过工具、不截断结果、不强迫编辑，仍允许读取缺失或过期源码。

专项与相关回归 74/74，全量回归 491/491，均无失败或跳过；Windows/Ubuntu 的 Node 20/22/24 CI 全部通过。服务器两组零模型调用预检验证候选确实能够触发提示。以上仅证明实现机制，不代表真实模型收益。

## 真实对照

相同官方 GLM-5.3-flash、思考设置、流式传输、任务初始源码和验收标准，原计划八次交错运行。第六次官方验收后触发事前冻结的质量止损条件：候选最多还能取得 2/4，基线至少已有 3/4，因此停止余下两次。

- 基线：已测 3 次，官方全部通过；Token 小计 3,497,530，151 次请求。
- 候选：已测 3 次，官方通过 1 次；Token 小计 5,682,088，270 次请求。
- 六次用量完整，无未知用量、无网络重试。未运行的各一次不算失败，也不计零 Token。
- 两次基线原生运行被时限取消，但其补丁通过独立官方验收；原生完成且官方通过，两组均为 1 次。不能将官方验收率等同于 Agent 正常完成率。
- 未完成整套八次，不报告整轮正确率变化或整轮 Token 收益百分比。这是两道已知题的小样本，不是完整 DeepSWE 分数。

逐次记录：Helm 基线 7/7、1,837,069 Token，候选 7/7、2,068,438 Token；Mnamer 第一对基线 370/370、460,970 Token，候选 367/370、2,232,420 Token；第二对基线 370/370、1,199,491 Token，候选 369/370、1,381,230 Token。失败样本完整保留，未筛选成功样本替代总结果。

## 为什么不能认定机制导致下降

三次候选的实际提示次数全部为零；初始请求哈希逐对相同，系统提示词和工具定义未变。触发前没有这条提示介入模型决策。样本之间存在生成路径波动，不能声称该提示导致下降，也不能声称它带来改善。

真正暴露的是触发范围不足：它只覆盖连续的完全相同请求和返回文本；不同查询、源码回执变化、穿插修改/测试以及原生命令都可能打断判断。候选 Helm 虽有 14 次相同参数的历史重复检索，仍不满足完整触发条件；参数重复数不等于无效检索数。

Mnamer 候选第一次的三个官方失败集中在 start/restart 生命周期；运行中也出现后台进程继承输出管道不关闭，属于相关风险信号，不能仅凭信号断言唯一根因。第二次仍漏掉日志使用嵌套状态路径的边界；自行编写的本地测试通过没有证明这一边界正确。候选第一次还出现 14 次 shell 错误、9 次测试错误以及四次补丁匹配失败，说明开销并非主要来自连续重复读取。

事后只读历史轨迹回放同样显示，该条件既可能漏掉失败路径，也可能触发于成功路径；回放不是模型实验，且未据此修改本轮冻结阈值。

下一步应先离线验证“验证失败类别与进展”信号的覆盖，区分命令策略拒绝、测试失败、后台管道未关闭和路径边界遗漏，再决定下一阶段；本轮不混入这些新改动，也不自动继续付费。
