# 大型任务 Token 增长：原因与解决方案

这是对既有 18 次大型任务记录的事后分析，没有新增供应商调用、没有修改运行时或排除任何样本。[结构化证据](large-analysis.json)。

## 先明确归因

观察到的新版大型任务累计增长是 **38.87%**，但目前不能归因于 GC 本身：这些任务没有压缩或 GC。重建两版首个请求的完整原生载荷后，18 个载荷的 SHA-256 全部与记录的供应商请求匹配；统一工作区路径后，9 对初始载荷完全相同，初始 Token 也相同，工具定义均为 2,280 字节。因此没有发现新增固定提示词开销。后续不同的模型决策导致了不同历史；代码版本、路径和供应商随机性等因果因素仍需在相同历史回放和功能消融中隔离。

## 增长分布

- 缓存键：88,031 → 140,505 Token，**增加 59.61%**，三次重复同方向回退。
- 重试预算：154,881 → 116,362，**减少 24.87%**。
- Unicode：49,228 → 148,836，**增加 202.34%**。
- 额外 113,563 Token 中，输入增加 110,906，占 **97.66%**；输出增加 2,657。
- 请求总数从 74 → 89，增加 **20.27%**；平均每次输入从约 3,902 → 4,491 Token，增加 **15.08%**。同时出现更多请求和更大历史。

Unicode 首次贡献了 83,216 的增长，但敏感性分析中同时移除该对两侧后，其余大型任务仍增加约 **10.76%**。该敏感性值不是正式结果，样本仍完整保留。

## 具体机制

### 1. 文件遍历被大目录占满

初始目录按名称深度优先扫描，最多 700 路径，随后才做任务相关排序。大量 src/generated 文件先占满额度，src/services 下的真正目标没有进入候选集。18 次大型任务的初始清单都没有目标路径；多次查询实际报告 scanned=700 files 且无匹配。includeOmitted 只扩大过滤范围，不提供续扫游标，重复查询仍可能扫同一批文件。

因此，“扫描额度内没有找到”会引出新的目录枚举、查询及猜测路径。它是两版共存的检索局限，这轮新版在缓存键及 Unicode 更频繁走入昂贵路径。

### 2. 一次目录输出，后续反复携带

list_files 默认返回 250 个路径；list_files(src) 的一次结果达到 **10,194 字节**，却仍没有目标文件。缓存键首次新版在第 3 次请求后持续携带此类大结果，后续发送上下文约 17–22 KB；旧版约 12–16 KB。

ContextOS 的总体软目标为 32,000 字节；大列表加上其他历史通常仍低于目标，因此没有被替换成引用。缓存键第三次新版最后发送 26,907 字节，列表继续驻留。仓库大不等于会话长：此次是多文件目录下的小修复，在结束前尚未达到语义压缩阈值。

两版各产生 8 个至少 10 KB 的目录输出，不能概括为“新版大目录调用总次数更多”；它们落在不同任务与阶段，后续携带轮数和检索决策不同，产生不同的累计输入。

### 3. 不可执行操作和过度修改扩大历史

新版大型任务有 **8 次 run_shell 失败**，旧版 1 次，例如目录命令、管道、内联脚本在当前非交互权限环境不能执行。失败会消耗一次调用并进入历史；当前 unit.error 被优先保留，已解决的操作拒绝仍可能持续占用上下文。

Unicode 首次新版有 17 次模型请求、20 次工具调用，旧版只有 6/6；发生多次补丁、两次验证，以及修改后又恢复 AGENTS.md。最终验收只确认最终文件范围与行为正确，**没有保证每一步操作都符合修改范围**。此次 100% 应解读为最终验收通过，不是过程零违规。

后期该样本的 ContextOS 投影曾从 27,820 → 29,724 字节：保留恢复工具和规则/目标锚点的成本使投影反而增大。现有收益回退条件只在 selected.length 非零且没有 stale 时生效，所以一些旧引用重新有效、规则修改后恢复等边界仍会带来额外开销。这是已有机制的局限，尚未证明由新版引入。

## 建议实施顺序

### A. 优先修复检索覆盖与输出体积

- 目录优先展示直接子目录与少量文件，限制默认字节数，显式请求仍可分页获取完整结果。
- 使用广度优先或目录轮转，让一个庞大子目录无法占满初始索引和搜索额度。
- 搜索返回覆盖范围、是否触顶及可继续的游标，重复同一查询可从未扫描部分继续。
- 根据任务词和已经看到的测试/import 证据排序；不要硬编码 services 或忽略所有 generated，确保跨语言、非 Git 与生成源码项目仍可覆盖。

这是最有证据支持的首选方向：减少找错范围和第一次进入历史的大输出。

### B. 为单个大工具结果设置历史保留预算

- 大目录/广泛搜索结果即使会话总量低于 32 KB，也可在最近窗口之后转成简短引用。
- 原始结果保存并可按页召回，保留路径范围、覆盖状态和版本；文件树变化时旧目录结果标为历史信息。
- 评估替换文本、工具定义、规则/目标锚点和预期召回成本后再采用，保持必要源码、未解决失败和最新验证证据。

它可保留现有 GC 与自动压缩，减少短修复过程中重复携带目录列表的成本。需要验证分页/召回是否反而增加轮数。

### C. 改善能力反馈与操作状态

- 在实际工具说明中明确当前可执行的目录读取与验证方式；非交互模式下给出可用的原生工具替代。
- 已经解决的权限/输入错误压成短状态，未解决测试失败与 pending-validation 继续保留。
- 通过任务中已观测的指令维护编辑边界，若已明确只能改某文件，拦截其他编辑并给出简短反馈；新任务重置、允许用户明确改变范围，保证泛化。

这能减少无效调用和反复修补，但反馈/约束本身也有开销，需独立评估。

### D. 用相同历史做机制对比，再做真实任务重复

- 用同一历史和源码版本比较两版生成的请求，隔离固定开销、历史选择和模型随机决策。
- 同一新版内分别测试 GC off/auto 和压缩 off/auto，记录发生修改、过期检查和恢复时的差异。
- 真实运行统一模型可见工作区路径、增加重复并加入新项目；记录检索覆盖、目录输出字节、失败操作、历史重复输入和最终/过程质量。

当前数据支持“检索和历史驻留存在可改善点”，不支持“GC 默认开启直接导致 38.87% 回退”。建议先做 A，每一步独立对比并等待审核。
