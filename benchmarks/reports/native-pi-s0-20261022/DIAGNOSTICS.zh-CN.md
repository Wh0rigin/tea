# S0 执行记录诊断与 S1 建议

以下结论来自已完成样本的工具调用、退出状态和官方验收反馈，不使用模型的私有推理内容。单个样本的解释不代表因果消融，也不代表完整基准成绩。

## 1. 后台行为的实现与自测缺少关键后置条件

样本：DeepSWE / Mnamer / TEA / 第一次重复。

- Agent 自行返回 `completed`、`validationPassed=true`，消耗 39 次模型请求、44 次工具操作；没有触发本轮请求数或工具数上限。
- 模型生成的 `start()` 先将状态写为 `running=true`、PID 写为启动进程自身的 PID，再启动 `threading.Thread(..., daemon=True)` 并立即返回。启动 Python 进程退出后，该守护线程不会独立存活，状态文件却能继续显示“运行中”。这与 [Python 3.12 官方线程生命周期说明](https://docs.python.org/3.12/library/threading.html#thread-objects) 一致。
- 新增 pytest **确实**通过 `subprocess.run([sys.executable, "-m", "mnamer", ...])` 调用了真实 CLI，包括 start/restart。不能把失败简单归因为“没有跑 CLI”。
- 但启动测试主要断言退出码及状态文件中的布尔值，重启测试主要断言退出码；没有在启动进程退出后验证后台持续工作、处理文件。这种自测能放过上述实现。
- Pi 同一任务的首个实现使用 `subprocess.Popen(..., start_new_session=True)` 创建独立工作进程，官方新增行为通过 51/51；TEA 为 48/51。双方原有行为均通过 319/319。TEA 剩余失败属于启动、未运行时重启、运行时重启三个生命周期用例，与这个实现缺口一致。

另有一项需要独立保留的执行证据：TEA 曾显式运行一个 CLI 探测命令并收到 `KeyError: 'movie_directory'`；工具记录中没有显式复跑同一探测场景。新增测试使用了不同的参数与工作目录，不能直接替代该场景的复验。这里不能把三个官方失败都归因于该 KeyError。

**更直接的改进对象**是验证目标：需要观察用户要求的持续行为，而不只是退出码、状态文件或自编测试数量。入口崩溃的记录与复验是补充的失败处理保障。

第二次 Mnamer 重复中，TEA 同样自行返回 `completed / validationPassed=true`，40 次模型请求后官方新增行为仅通过 33/51，原有行为通过 319/319。失败用例涉及搬运文件、默认状态路径、持久化恢复、去抖、日志以及离线执行等多类行为。因此，修复首个样本的线程设计并不能直接证明整项能力恢复；还需要覆盖公开需求中的默认值和行为组合。两个 Mnamer 样本的模型摘要调用数均为 0；本轮仍开启 ContextOS 的其他机制，没有做组件消融。

## 2. 官方验收与客户端完成状态必须分别报告

样本：DeepSWE / Helm / TEA / 第一次重复。

- 官方验收通过新增行为 5/5、原有行为 2/2；客户端状态仍为 `needs_validation`。
- 未解决记录包含广范围 Go 测试及带 `-update` 的调用。部分子包不支持该参数，该调用被尝试三次。
- `go test ./pkg/action/...` 的失败中有依赖外网的测试，也出现过断言不符。后来的窄范围通过不能直接证明广范围检查已通过。

因此，不能把 `needs_validation` 直接说成误报，也不能因为某个测试出现网络问题就将整条广范围测试都标成“环境不可用”。官方验收覆盖其指定的功能与回归用例，不等于项目所有测试都已通过。

## 3. 长任务的更多轮次能抵消每轮较短的上下文

首对 Helm 均通过官方验收且用量完整：

- TEA：92 次模型请求，1,936,867 Token。
- Pi：59 次模型请求，1,311,650 Token。
- TEA 请求数多 55.93%，每请求平均总 Token 略低，但累计 Token 多 47.67%。

这说明只压缩单次请求还不够，需要减少低效的检索、重复报错和复验轮次。两侧保留了不同的工具粒度、命令权限与上下文策略；这里不能把全部差异归因于 ContextOS 或某一种工具。

## 4. 重复测试会改变单次实验给出的印象

FastAPI 功能任务两次重复双方均通过 4/4：

- 第一次：TEA 315,358 / Pi 256,899 Token，TEA 多 22.76%。
- 第二次：TEA 289,654 / Pi 399,927 Token，TEA 少 27.57%。
- 两次合计：TEA 605,012 / Pi 656,826 Token，TEA 少 7.89%。

因此不能取某一次的最大收益当作稳定效果。两个重复仍是小样本；后续候选需要同配置、固定任务与交错顺序的对照，不能只挑已有优势的题。

## 5. 失败、超时与未知用量各有不同含义

- WorkBuddy / Pi / 第二次 Black：最终达到全局时限，官方通过 1/6。已独立核对的 2,226,438 Token 保留在全部尝试记录中，但不计入双方成功的收益条形图。过程中曾执行没有显式单独超时参数的参考包下载命令，等待时间较长。
- WorkBuddy / TEA / 第一次 Blog Tags：HTTP 200 流缺少 `message_stop`，最终用量未知；留下的代码官方通过 12/20。
- DeepSWE / Pi / 第二次 Helm：同样缺少 `message_stop`，用量未知；留下的代码仍通过官方 7/7。

缺少完整结束事件时，即使出现 0/0 用量字段，也不能当作已知零消耗。前两次缺失结束事件的响应分别保留 10 USD 控制预留，没有自动重试。当前审计不能进一步确定这两次上游响应不完整的具体原因。

另有 DeepSWE / TEA / 第二次 Helm 达到全局 30 分钟时限，取消了正在进行的请求。该请求的服务端记录为写回客户端时出现 BrokenPipeError，最终用量未知；这属于截止取消情形，应与前两次响应自行结束但缺失结束事件区分。该样本同样保留 10 USD 预留，没有重试。

## 6. 当前 S1 的建议边界

优先落实“验证可观察的后置条件”，并补充真实入口崩溃的记录与复验，再测实际解题率：

1. 在现有任务回合内，将公开需求简要对应到可观察的验收项，包含明确约定的默认值与必要行为组合，不把官方隐藏测试名或参考实现写入提示。对持续运行、异步处理等任务：在启动调用退出后，从独立进程验证实际处理、持续活动与停止行为。不能以状态字段或启动退出码代替目标行为，也不新增固定的冗长规划回合。
2. 从项目元数据或已确认的工作区入口识别实际 CLI，不在引擎中硬编码 Mnamer、特定线程写法、异常字段或这些测试名。
3. 将入口的未处理运行时异常加入待验证状态，保留命令及失败引用；普通检索无匹配、预期的非零退出和正常参数校验不能一概当作源码失败。
4. Agent 尝试正常结束且该状态未解决时，提供简短的事实反馈，引导修复后再次执行实际入口；沿用已冻结的预算与超时边界。
5. 让待验证状态跨会话恢复、压缩和 GC 保留。源码改动本身不能代替复验通过。
6. 对正常成功的小任务避免增加固定规划回合和冗长提示。实际 Token 与解题率变化由新对照判定。

专项覆盖应包括“启动返回成功且写入 running，但实际后台不存活”的反例、入口崩溃后窄测试通过、入口修复后真实复验通过、预期失败探测、普通搜索失败、会话恢复及压缩/GC。再执行完整回归与真实任务对照。

本轮 S0 不实施这些产品改动。S0 报告审核后再进入 S1；单元测试通过不能替代真实解题率与 Token 收益的测定。
