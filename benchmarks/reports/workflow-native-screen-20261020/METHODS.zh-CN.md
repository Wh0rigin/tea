### 新增专项发现的既有缺陷

真实任务触发了一个原有回归套件未覆盖的进程问题：直接子进程退出、后台后代仍持有 stdout/stderr 时，工具一直等待 `close`。杀直接子进程无法释放这些管道，超时和取消都可能无法按时返回，Agent 因而拿不到反馈继续修复。

[独立复现数据](pipe-repro.json)使用不调用模型的自编用例，在 Windows Node 24.14.0、Linux Node 20.18.1 / 24.12.0 上分别运行两版源码的超时、取消场景。12 个场景均复现：设置 300ms 后，到 1,200ms 仍未返回，只有清理该用例自己创建的后台后代才结束。它们是**失败的行为边界检查**，不能写成“全部专项通过”。[复现脚本](pipe-repro.mjs)应在隔离容器中运行。

实验期间保留原始源码快照，不混入修复。该问题同时存在于父版本和候选版本，不是本次工作流改动新引入的回归。

## 真实任务样本

- DeepSWE v1.1：两道以前测过的仓库题，各版本各重复两次，共 8 次。原生 Pier 执行、独立官方判定。它是已见任务的回归子集。
- WB-Bench-Code：从官方 80 道 Code 题中，以固定任务 ID 哈希顺序抽取前四个不同类别，各版本各重复两次，共 16 次。类别为缺陷修复、Python 迁移、功能开发、产品数据分析。抽样在获得这些题的模型运行结果前完成，不依据结果换题。
- WorkBuddy 使用自定义串行调度调用原生 Harbor Trial，保留官方 CompositeVerifier。它不是官方完整榜单提交，也不覆盖 Web、Office、Security 赛道。

每次运行使用全新容器和同一内容 ID 的初始镜像。任务原始说明、工作区归档和 Dockerfile 均保留哈希；镜像内实际 Git HEAD、源码树也固定下来，不把数据集里的历史提交字段直接当作镜像 HEAD。

## 共同参数

GLM-5.3-flash、流式、enabled thinking、low effort，最大输出 131,072，推导思考预算 8,000，本地上下文窗口 216,000，保留量 4,096，ContextOS 目标 32,000 字节，自动压缩与 GC 开启。最多 96 次工具调用、128 次传输请求，单请求超时 900 秒，单题 Agent 执行 30 分钟。

当前运行时会为最大输出预留空间，因此普通任务请求的输入保护容量为 `216000 - 131072 - 4096 = 80832` 估算 Token。216K 是配置的总窗口，不代表这组参数能同时携带 216K 输入。两边受相同限制；结论也受这一配置影响。

每次预留 10 USD 的控制额度，两组最多分别为 80 / 160 USD，合计 240 USD。它们是实验限制，不是实际账单。控制费率也不是账单证据。所有失败与未知用量保留；未知计费保留整次额度，不自动重试。

## WorkBuddy 环境适配

这些适配在其真实模型调用之前完成，双方一致使用，写入冻结协议：

1. 原始 Dockerfile 通过临时下载转发构建，随后固定完整镜像 ID。服务器 Docker 未重启，模型调用通过独立 Unix socket 转发；容器中没有真实 API 密钥。
2. 现有 Docker 无法解析原 Compose 的 `host-gateway`，用单独的 Compose 覆盖文件清除这一未使用的主机映射。原题目文件不改。
3. Agent 使用 `dev`。官方转换器生成的临时验证脚本为 0600，`dev` 无法读取，因而验证阶段使用 root。断言和计分规则不变。
4. FastAPI 原始镜像安装的 pytest / AnyIO 超出了项目公开声明的测试范围，导致收集阶段中止。兼容层固定 pytest 7.4.4、AnyIO 3.7.1、Trio 0.23.2；源码树保持相同。原始镜像与兼容镜像 ID 均记录，没有屏蔽警告或删除检查。
5. 在注入隐藏测试前，以 Git 差异保存真实的已跟踪及未跟踪修改到判定器要求的 `pre_injected_agent.patch`，支持“必须补测试”的检查。该步骤不改变源码、索引或 HEAD。

两边实际工具链均通过了不调用真实模型的 SSE 预检。四道原始题的官方判定器也用不修改源码的空操作 Agent 做过环境检查；其分数只说明判定器能工作，不算 TEA 解题成绩。环境适配限制了与其他公开榜单直接比较的意义。

## 统计与验收

- **整题通过**与**部分检查通过**分别报告。DeepSWE 以官方完整 reward 为准；WorkBuddy 以官方 reward / full-pass 为准，均值 reward 与整题通过率不能混用。
- 使用供应商实际报告的输入、缓存读取、缓存写入和输出；缓存输入计入一次。思考若已包含在输出中，不再重复相加。
- 比对 TEA 账本与独立传输记录的请求数量、请求哈希、用量和控制参数；缺失终止事件或无法对账的用量为未知。
- 全部尝试的用量用于描述实验消耗。只有两边都完成并通过、源码及说明一致、用量完整的配对，才用于“完成相同工作节省多少 Token”的结论。
- 失败样本不会混入成功工作流的 Token 条形图；失败和未知样本仍逐条展示。没有合格配对时不生成节省百分比。
- 不把 DeepSWE 和 WorkBuddy 的不同计分尺度拼成一个总正确率，也不从少量题目推断完整基准得分。

另一个零模型调用诊断仅在原始固定源码上重放八项已记录成功的编辑，随后用原生官方判定器检查。它不是完整终态文件系统恢复，结果单独保存在 [deepswe-postmortem-diagnostic.json](deepswe-postmortem-diagnostic.json)，不补入原始成绩、成功率或效率分母。
