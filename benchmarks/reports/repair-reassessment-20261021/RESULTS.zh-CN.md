# 修复包真实解题率与 Token 收益复测

## 结论：局部有效，整个包未达到“保持正确率并节省 Token”

本轮固定同一模型、思考等级、任务初始源码、镜像、权限和限额，**重新运行对照与候选**，完成 **24/24 次尝试、825 次供应商请求**。请求数、哈希、usage 与控制参数全部对账；未知用量 0，付费重试 0。24 份官方评分记录中有 1 份为 `build_error` 的零分回退，未完成常规检查，详见下文。旧实验与旧的未知计费预留保持原状。

- **DeepSWE v1.1 子集**：官方整题通过 **1/4（25%）→ 0/4（0%）**，下降 **25 个百分点**。所有尝试消耗 **3,359,152 → 2,609,223 Token，减少 22.32%**；没有双方都完成且整题通过的配对，**不能据此证明同等工作量的节省**。
- **WB-Bench-Code 子集**：官方整题通过 **5/8（62.5%）→ 3/8（37.5%）**，下降 **25 个百分点**；官方任务得分均值 **0.7875 → 0.7048**。所有尝试消耗 **3,220,424 → 2,048,101 Token，减少 36.40%**；正确率同时下降，**不能称整体优化成功**。
- **有效成功工作比较**：只有 Black 修复题的两个配对符合双方完成、官方满分和完整计量条件，合计 **1,465,967 → 1,249,870 Token，减少 14.74%**。两次分别减少 **1.30% / 31.42%**；仅一种任务、两次重复，不能推广到所有编码任务。

候选是 `d0b566b`，对照是修复前 `5cb5198`，不是之前的历史父版本。比较的是工具可靠性修复与通用真实入口指导组成的整个包，**不能把成绩变化单独归因于某一行提示或某一项修复**。

## 1. 为什么需要重新运行基线

上一轮可见轨迹已经表现出大幅波动。本轮首个 Helm、Black 基线请求，与上一轮相同运行时代码的候选请求，**首请求哈希和模型控制参数完全相同**，后续轨迹仍不同。这个核对没有添加模型调用，仅覆盖这两个首请求，不能证明所有运行可确定复现。[核对记录](historical-baseline-equivalence.json)

例如，新的 FastAPI 对照同样得到官方 4/4，两次却分别消耗 **1,001,940 / 313,370 Token**。用历史一次较低或较高消耗对比新候选，都可能夸大收益。这里保留冻结顺序的两次重复，不挑最好的一次，也不替换失败。

## 2. DeepSWE：新功能覆盖与上下文保护仍有缺口

### Helm 清单流

- 对照第1次：新增检查 **0/5**，已有检查 **2/2**，`tool_limit_reached`，**836,891 Token**；96 次工具调用，无成功编辑。
- 候选第1次：**0/5 + 2/2**，`failed / MODEL_CONTEXT_LIMIT`，**848,833 Token**；95 次工具调用，无成功编辑。
- 对照第2次：**0/5 + 2/2**，`tool_limit_reached`，**951,237 Token**。
- 候选第2次：**0/5 + 2/2**，`failed / MODEL_CONTEXT_LIMIT`，**640,801 Token**。

四次都没有完成需求；检索循环仍存在。按相同证据头识别的相同版本、相同行范围完整重复读取，在对照两次为 **30 / 16** 次，候选为 **24 / 10** 次。这只是可见工具行为诊断，不能当作模型内部思考解释。

候选两次均出现压缩请求输出 `max_tokens`，摘要不完整因而未采用，随后估计输入 **89,015 / 117,661** 超过 **80,832** 的输入保护。第1次较早的另一份摘要曾成功采用，不能说自动压缩从未运行。

压缩请求实际上限 **1,200 Token**，派生 thinking budget **1,199**；截断请求恰好报告输出 1,200。任务请求上限仍是 131,072，两组策略相同。**216K 是总上下文配置，不是纯输入容量**：任务输出预留与额外 4,096 保护后，当前输入保护为 80,832。完整摘要与安全降级没有衔接好，是本轮明确暴露的旧策略问题；不能仅靠继续放大任务输出上限解决。

### mnamer 日志守护

- 对照第1次：新增检查 **51/51**、已有 **319/319**，`completed`，**795,209 Token**。
- 候选第1次：新增 **33/51**、已有 **319/319**，`completed`，**764,892 Token**。
- 对照第2次：新增 **47/51**、已有 **319/319**，`completed`，**775,815 Token**。
- 候选第2次：新增 **50/51**、已有 **319/319**，`completed`，**354,697 Token**。

候选第2次只剩实际守护进程启动、状态和停止行为的一项失败，但整题仍未通过；第1次对实际守护、持久化、文件处理等覆盖不足。已有 319 项检查全部通过，不能掩盖新增功能失败，也不能将拼接后的高部分通过率写成整题解题率。

本轮四个日志样本都正常返回；对照也没有复现上一轮的管道卡住，**不能把本轮这一现象单独归功于新修复**。命令有界返回的确定性证据仍来自独立专项。[专项记录](../runtime-repair-20261021/verification.json)

## 3. WB：减少工作量不等于提高效率

### Black 修复：唯一可比较的完整成功工作

- 第1对：双方 `completed`、**6/6**；**811,924 → 801,329 Token（−1.30%）**。
- 第2对：双方 `completed`、**6/6**；**654,043 → 448,541 Token（−31.42%）**。
- 合计 **−14.74%**，两次差异明显；它支持这个已见修复题的局部观察，不能证明普遍或稳定的收益。

### FastAPI 功能：少耗 Token，但少完成需求

对照两次均 **4/4**，候选两次均 **1/4**，失败均涉及应用入口、路由入口及带前缀路由。对照消耗 **1,001,940 / 313,370**，候选 **213,529 / 167,006 Token**。候选第2次补丁只涉及路由实现和自己的测试，没有修改应用实现。

候选两次自行验证通过并宣告完成，却未覆盖真实集成契约。通用的“验证真实入口”指导没有形成足够可靠的覆盖约束。大幅下降的消耗包含未完成工作，不能作为效率成绩。对照第1次虽然官方满分，自行运行的其他测试仍有未解决失败，结束为 `needs_validation`；该区别保留，不改写为完成。

### Python 迁移：局部成绩提高，消耗反而上升

对照 **14/20、12/20**，候选 **19/20、13/20**，均未满分。两次用量分别 **34,075 → 54,395（+59.63%）**、**41,721 → 228,040（+446.58%）**。模板标签、正文与站点标题等契约仍有遗漏。候选较多编辑和自测并没有稳定换来完整实现；不能只用第一次 19/20 代表此任务。

### 注册漏斗：替代验证有效，业务正确性仍不稳定

- 第1次对照 **13/13**、`needs_validation`、**114,955 Token**；候选 **13/13**、`completed`、**66,986 Token**。候选在 pytest 缺失后用实际非零 unittest 检查完成验证，仍明确保留原 pytest 命令未验证。该流程恢复确实发生，但对照未完成，按预定规则不进入成功工作 Token 柱形图。
- 第2次候选 **7/13**、`completed`、**68,275 Token**，说明替代验证不等于业务正确性保证。
- 第2次对照 **248,396 Token**；产出结构使官方评分器抛 `TypeError: string indices must be integers, not 'str'`，官方包装回退为 `build_error`、0 分、0/1。**常规 13 项检查没有完整执行**；不是 Linux 镜像无法启动，也没有重试或自行改判。

“官方满分且 Agent 完成”两版本都为 **3/8（37.5%）**，与官方整题通过 **5/8 → 3/8** 是不同指标：验证恢复改善了一个案例，不能据此覆盖另一个案例的代码退步。

## 4. 对下一步的判断

1. **整个包尚未通过质量门槛。**不应把全量 Token −22.32% / −36.40% 写成保持正确率的性能提升，也不据此推荐整包作为省 Token 升级。
2. **先拆分因果。**工具可靠性修复有专项支持；通用入口提示与工具修复应分开做消融，不能凭当前混合比较判定是哪一项导致退步。
3. **压缩需要单独控制。**分别评估摘要输出空间、思考配置、摘要被拒后的恢复，以及输入/输出预留策略。保留历史的正确保护不能变成无法继续的唯一结局。
4. **让需求覆盖可核查。**在修改前后对照实际入口、输入输出契约和需求边界；不能只增加自写简化测试或无止境扩大测试范围。新方案需要另外冻结，再比较官方整题通过和成功工作用量。
5. **控制检索不收敛。**用证据版本、范围与已尝试策略识别重复读取，提供转向反馈；不能用提前停止制造更低 Token。Helm 的两组失败说明单纯放宽文件搜索参数还不够。

以上是后续实验建议，**本轮没有据评分中途修改 Agent，也没有追加付费运行**。
