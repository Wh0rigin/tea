## 结论

三项均完成实现和验证，但仅保留结构化错误记录。独立摘要预算、截断修复与紧急压缩未通过本轮采纳门槛，已从默认运行时回退。完整试验代码可在提交 `fb4fa1120ab4dd4deaf73f78263901475ee1de4f` 查看，最终 PR 差异不包含这两项行为。

固定两题各一次的受限条件试跑中，原版与候选版的官方验证结果均为 0/2；累计 provider Token 从 141,648 增至 371,303，增加 162.13%。没有任务完成，也没有代码修改。这个结果不支持发布节省 Token 或编码正确率提升的结论。

此外，题目明确要求新建分支，而两轮使用的同一审批策略可能拒绝对应 Git 操作。该协议存在任务要求与可用能力不匹配的问题。这是诊断性试跑，不是完整 113 题成绩，也不能据此判断不受这些限制时的编码能力，或断言恢复机制普遍无效。

## 三项分别发生了什么

### 1. 结构化错误记录：保留

以往 `ModelError` 在内部捕获后仅发给 `onText`。包装器没有这个回调时，返回结果只含 `failed`，丢失停止原因。

现在错误会出现在返回值、`summary.json`、账本及 `agent_error` / `turn_end` 事件中，包含停止阶段、是否提交请求、本地估算、输入上限、请求字节和压缩次数。记录不含请求正文、认证头或堆栈，配置中的凭据被脱敏。UI 回调抛错也不会替换真正的执行错误。未知用量在临时会话中同样保留，不触发自动恢复。

本轮两题都明确记录 `MODEL_CONTEXT_LIMIT`，且未提交被拦截的下一次请求：

- Helm：估算输入 35,957 > 24,576；正常压缩两次、紧急压缩一次。
- mnamer：估算输入 29,340 > 24,576；正常压缩两次、紧急压缩一次。

这些是本地估算与保护行为，不是 provider 报告的真实上下文容量。

### 2. 独立摘要预算：实现过，未默认保留

试验默认摘要输出 2,048、思考预算 1,024；截断时最多修复一次，最多提升到主请求输出上限 4,096。请求仍经过同一适配器、账本和费用保护。

原 Python 样本的摘要曾以 `max_tokens` 结束，消耗恰好 1,200 个输出 Token。候选的六次摘要均成功采用，没有截断，也没有触发实际付费修复。截断修复路径由确定性专项测试覆盖。

消除了这个中间故障，但没有转化成代码修改或验收提升；不将其作为本轮已验证有效的默认优化。

### 3. 有界恢复：实现过，未默认保留

试验将失败后的整轮禁用改为按历史增长冷却，并保留常规两次上限；达到硬上限时额外允许一次较小完整前缀的紧急压缩。

两题都实际触发并成功执行紧急压缩：Helm 82,557 → 54,044 字节；mnamer 77,288 → 53,701 字节。这是当时请求体大小的变化，不能当作真实 Token 节省率。

随后持续读取和召回让上下文再次增长，最终仍被保护机制停止。该方案在本轮延长了未完成的轨迹，未带来验收收益，因此回退。
