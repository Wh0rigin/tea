# 会话压缩

[English](COMPACTION.md)

TEA 可将旧对话整理成摘要，让后续请求接收“摘要＋近期消息”。它与 `compact-tools` 是两项独立能力：后者只缩短部分旧工具输出，不调用模型生成会话摘要。

设计参考 [Pi 0.87.1 的会话压缩文档](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/docs/compaction.md)：选择安全保留边界、继承已有摘要、生成结构化上下文、保留原始对话。实现由 TEA 自行编写，没有引入 Pi 源码。

## 使用方式

在交互终端中输入：

```text
/compact
/compact 保留 API 兼容要求和仍未解决的失败。
/status
```

即使自动压缩关闭，仍可手动压缩。启动时开启自动压缩：

```sh
tea --interactive --compaction auto --max-cost-usd 0.10
tea "修复重试预算" --compaction auto --max-cost-usd 0.10
```

仍需配置真实调用的凭据和价格。离线终端演示不会生成模型摘要。

## 对话与模型输入分开保存

- 默认检查点 GC 将已覆盖原文保留在加密存储中，内存仅保留后缀和原文要求；`--memory-gc off` 时原始数组保持完整。后续请求使用摘要、要求与近期消息。
- 一批工具调用及其对应结果作为完整组保留，切分不会拆开它们。ID 歧义、孤立结果、未完成工具批次会阻止压缩。
- 始终保留最新完整消息组，即使它超出近期字节目标；更旧的完整组只有放得下才加入，避免一个过大的旧批次长期占住近期上下文。如果最新用户请求落在被摘要的部分，后续请求也会附上其原文。
- 再次压缩时，输入包含已有摘要，以及上次保留边界之后的旧消息，避免重复发送已经摘要过的原文。
- 摘要包含目标、约束、进度、决定、下一步和关键上下文。待验证修改和验证状态由运行时单独附上，摘要不能把未验证任务改成完成。
- 摘要请求中的历史工具结果保留约 2,000 UTF-8 字节的头尾，以及省略说明和哈希；大段补丁参数也有边界。普通用户文本不会为了塞进摘要请求而截断。
- 压缩成功后清理源码读取引用缓存，下一次读取会重新返回源码，避免引用已经从模型输入省略的旧行。已学习会话词表和待验证状态保留。
- `/new` 清除摘要和会话词表，适配器费用及待验证修改继续保留。

原文、摘要和运行状态支持本地持久化恢复；默认 GC 释放已归档正文。详见[内存与磁盘 GC](MEMORY_GC.zh-CN.md)。默认账本只保存摘要哈希、数量和边界。`TEA_STORE_RAW=1` 才会在本地压缩记录中增加摘要和尝试操作的文件路径，并继续使用原有原始请求存储机制。

## 自动触发与资源边界

自动压缩默认开启，可用 `--compaction off` 关闭。每次编程请求之前，TEA 测量包含系统提示、工具定义和控制参数的**完整请求 UTF-8 字节数**，达到输入保护上限的 80% 时尝试压缩。

Pi 按模型上下文 Token 容量触发；TEA 尚无原生 tokenizer 和服务商模型上下文目录，因此这里使用字节保护，不能称为准确 Token 阈值。

- `--compaction off|auto` / `TEA_COMPACTION`：默认 `auto`。
- `--compaction-keep-recent-bytes N` / `TEA_COMPACTION_KEEP_RECENT_BYTES`：默认请求字节上限的 30%，须为正安全整数。
- `TEA_COMPACTION_TRIGGER_RATIO`：默认 `0.8`，严格大于 0 且小于 1。
- `TEA_COMPACTION_MAX_PER_TURN`：默认 `2`，范围 1–8，限制一次提交任务中的全部自动尝试，包括未成功尝试。手动命令最多发送一次摘要请求。
- 原有 `TEA_MAX_REQUEST_INPUT_TOKENS` 是序列化输入字节保护配置；其名称不能当作精确 tokenizer 上限。

摘要复用同一个适配器、模型和思考等级。输出上限为 `min(TEA_MAX_OUTPUT_TOKENS, 1200)`，enabled 思考预算按该上限计算，与普通请求遵循相同公式。摘要过程中不执行工具。

如果计划摘要的部分无法全部放入请求，先摘要能放入的最长完整前缀，并标记为部分压缩；剩余自动尝试可以继续推进边界。过大的最早用户消息可能导致摘要不可用。最近的完整消息组仍可能超过请求保护上限，此时编程请求会由原有保护停止。

## 费用、失败和收益判断

摘要请求与编程请求共享费用和累计输入预算。服务商 usage 计入主总量，同时通过 `purpose: "compaction"`、`compactionRequests`、`compactionInputTokens`、`compactionOutputTokens` 单独标记。摘要用量不完整时，实际 Token 字段为 `null`，`reportedCompactionInputTokens` 和 `reportedCompactionOutputTokens` 保留已报告下界；脚本化用量不会发布为真实服务商 Token。摘要未采用也要计入已发生的请求费用。

只有摘要正常结束、按顺序包含所有要求章节及其内容、不请求工具，且能缩短后续完整请求时，才采用新摘要。尺寸比较包含摘要包装、最新用户原文、运行时状态和开启的 `compact-tools` 请求视图；它不能证明净 Token 节省，也不能自动验证摘要的语义完整性。

在写入检查点账本前检测到取消，以及不完整摘要、章节缺失和无尺寸收益，都会保留原有上下文及原始对话。如果取消发生在最后的账本写入期间，写入成功后仍采用已经完成的检查点，与已完成的工具操作一致。适配器错误会停止当前任务，未知用量保留完整费用预留。当前恢复发生在请求发送前的本地字节检查；服务商溢出且计费不确定时不会自动重试。

实测需要计算摘要开销、任务验收、重复次数，并固定初始仓库及模型控制参数。[2026-10-11 专项报告](../benchmarks/reports/compaction-glm-20261011/README.zh-CN.md)记录了 41 项专项测试和 GLM-5.3-flash 配对测量：固定历史压力配置净节省 72.33%，模型生成历史的检查/修复多轮任务净节省 63.14%，均计入摘要开销；复测 16/16 通过验收。样本是自编 JavaScript 项目，每案例两轮，采用 35% 实验阈值，不能证明默认配置收益或未见仓库的泛化能力。实测引擎与后续离线验证的 UTF-8 修复在报告中分别标明。


常驻历史达到 4 MiB 也会触发自动压缩；这是序列化历史阈值，不是进程堆的硬上限。
