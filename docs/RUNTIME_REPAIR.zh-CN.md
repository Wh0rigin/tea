# 基准失败后的执行与验证修复

日期：2026-10-21。修复基于[本轮基准分析](../benchmarks/reports/workflow-native-screen-20261020/RESULTS.zh-CN.md)，原始 24 次真实成绩保持不变。没有追加付费模型运行，没有宣称本轮已经提高解题率或节省真实 Token。

## 1. 测试失败与运行器缺失分别记录

真实场景里，pytest 未安装，unittest 已通过，旧控制器仍要求原 pytest 命令再次通过，导致反复执行不存在的运行器。

现在分为两类状态：

- `validationFailures`：已经观察到的失败、零测试、拒绝或未完成执行。必须对应原命令通过，其他局部成功不能清除。
- `validationUnavailable`：有明确启动前证据的运行器不可用。识别结构化的可执行文件 ENOENT，以及 Python 启动时输出的单行 `No module named pytest/unittest`；测试内部的 ImportError、应用依赖缺失和普通断言失败不进入这个分支。

只有相同语言工具链的替代命令实际成功，且输出包含非零通过测试的摘要，才解除该环境阻塞。空输出、零项测试、全部跳过、另一个语言的测试或单纯 lint 成功不能替代。已存在的源码失败继续独立阻塞。

**这不证明两个测试框架的覆盖等价。** 原命令继续列为未验证，另记实际通过的替代命令；结果对象、工具反馈、最终文本和终端 `/status` 都显示这个限制。只有原命令后来实际成功，才删除其不可用记录。

新修改或检测到工作区/HEAD 外部变化后，旧替代通过标记失效，要求新验证。失败与未验证记录经过会话恢复、`/new`、摘要和 GC 保留。旧会话没有失败分类证据的记录保持保守，不能自动降级为环境问题。

## 2. 命令超时和取消能够有界返回

旧执行器等待子进程 `close`。直接进程退出后，后台后代仍持有输出管道，导致超时或取消无法返回，Agent 得不到反馈。

修复内容：

- POSIX 为命令建立独立进程组；直接进程仍存活时，超时/取消终止该组。Windows 保留 `taskkill /T /F`，给清理程序有界时间完成。
- 超时、取消与输出排空分别有界；不再无限等待后代关闭管道。
- 直接进程退出后，输出管道 500ms 仍未结束，则报告 `EXECUTION_INCOMPLETE`，保留有限的已采集输出，**不授予验证通过**。
- 超时/取消保留部分诊断，并移除计时器、监听与输出句柄。直接进程已退出时不再延迟按其 PID 杀进程，避免影响其他工作。

清理时间也计入工具耗时；Windows 最坏可额外等待约 1.75 秒。脱离进程组或在父进程退出后留存的后代不保证全部清理；反馈明确说明后台工作可能仍存在。这里修复的是工具无法返回，不是实现 OS 级完整作业隔离。

## 3. 搜索接受具体文件

模型曾多次向 `search_code.path` 传入具体文件，工具只接受目录，产生无效往返。现在目录和单个文件都能搜索，保留行号续页、扫描字节/大小上限及源码哈希证据。

检查请求路径与真实解析路径；密钥文件、Git/TEA 存储、越界路径及指向这些位置的链接仍拒绝。`list_files` 仍要求目录，没有放宽命令权限。

这消除了一个明确的工具适配障碍，尚未证明能解决大型任务反复检索、迟迟不修改的问题。

## 4. 真实入口覆盖指导单独提交

核心修复提交为 `da5faeb`。随后独立加入一条通用指导：使用已有输入验证实际入口与需求边界，不能只验证自己编写的简化样例，并区分运行器不可用与测试断言失败。

指导没有加入任何基准题名称、隐藏检查或修复答案；它是模型工作方式的提示，不是运行时证明“需求全部覆盖”。与核心修复分开提交，后续可以单独对照其解题质量与开销。

静态小目录提示+能力说明+工具定义合计 **5,246 → 5,420 UTF-8 字节（+3.32%）**；宽目录 **5,482 → 5,656（+3.17%）**。其中指导增加 189 字节，搜索说明减少 15 字节。错误状态附加记录的动态开销不包含在这里。这些都是离线字节，不能当作供应商 Token。
