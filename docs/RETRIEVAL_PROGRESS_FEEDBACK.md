# Retrieval progress feedback experiment (priority 2)

Default-off candidate from production `a3571e5`, with no PR24 prompt or priority-1 recovery changes. Enable only with `TEA_RETRIEVAL_PROGRESS_FEEDBACK=1` or SDK `retrievalProgressFeedback: true`. PR16 numeric settings, ordinary compaction cap, tool definitions, permissions and verification rules stay unchanged. The option is visible in profile overrides.

The observer tracks SHA-256 digests of canonical tool inputs and actual returned text for structured retrieval tools: read_file, search_code, list_files, recall_context and search_history. Every lookup still executes normally. After three consecutive repeats of previously observed identical request/result text, it may append one advisory text block after the batch's unchanged tool-result blocks. A new query/result, error or any non-retrieval operation breaks the streak. A new compaction checkpoint clears comparisons. At most two notices per turn, separated by at least twelve retrieval observations; at most 64 digest entries. State is not shared across user turns, sessions or projects, and contains no retained source bodies.

The feedback asks the model to reuse evidence only if still visible, otherwise change query/scope or read the needed range. It explicitly permits rereading missing/stale evidence and says repetition does not prove freshness. It neither blocks repeated calls nor forces edits or completion. If later results in the same batch are novel, no notice is emitted. Model autonomy and exact-source patch safeguards remain authoritative.

Raw results, hashes, source dependencies and ledger tool observations are unchanged. The notice is separately recorded as retrieval_progress and carried as text after tool results; it is not a new user requirement or validation proof. It can add prompt traffic and can be ignored. It deliberately does not interpret native shell commands, semantic query equivalence or a changed tree from an unchanged search output. Identical parameters/results alone do not establish that a repeat was useless.

Self-authored tests cover repeat/cooldown/cap bounds, new evidence, checkpoints, operations/errors, bounded digest memory, default-off numeric-profile preservation, actual list_files execution with unchanged outputs/call counts, mixed-content protocol validity, ContextOS assembly and pending validation. They establish mechanics, not a model/token gain. Existing evidence-residency tests already invalidate receipts when actual source is absent; this experiment does not reimplement that fix.

Live gate: same pinned production parent, model/effort/endpoint/streaming/tasks/initial sources/acceptance, interleaved repetitions; record actual notice activation, all attempts, official vs native completion and provider usage separately. Reject lower token totals accompanied by worse acceptance. No benefit claim if the mechanism never activates. Keep unknown use unknown and retain reservations. No production adoption before review.
