# DeepSWE 216k 后续试跑复盘

日期：2026-10-19。

## 结果：有功能进展，整题仍未通过

本轮沿用最初预选的两道官方仓库任务，各一次真实模型执行。**整题通过 0/2**，不能发布为完整 DeepSWE 分数，也不能表述为编码正确率提升到某个通用百分比。

- **Helm**：官方新增功能报告项通过 **3/5**，原有行为 **2/2**；修改四个文件，达到 **96 次工具调用**上限。用量 **1,525,396 Token / 61 次请求**。
- **mnamer**：官方新增功能报告项通过 **47/51**，原有行为 **319/319**；修改四个文件，55 次工具调用后 TEA 标记完成。用量 **625,476 Token / 41 次请求**。自己的验证通过，官方整题未通过。
- 总计 **2,150,872 provider Token、102 次请求**，用量全部完整并与转发次数对账。输入含缓存 2,124,629，输出 26,243；缓存读 496,640 已包含在输入中，不再重复相加。控制费率估算 **1.7731836 USD**，不是实际账单。

Helm 的 5 个新增报告项包含父测试与子测试，不能理解为五个独立任务。也不能把大量既有测试的通过率当作新功能完成率。

之前 32k 受限试跑没有代码修改，新增报告项分别通过 0/5、0/51。本轮的功能覆盖有进展，但整题成绩仍是 0/2。窗口、评测 Git 合同和随机轨迹同时改变，因此不计算两轮的 Token 优化百分比。

完整配置、任务源码基点、镜像、哈希、补丁恢复校验与聚合数据见 [实验记录](../benchmarks/reports/deepswe-context216-20261019/README.md) 和 [results.json](../benchmarks/reports/deepswe-context216-20261019/results.json)。

## 扩容实际验证了什么

源码固定为 `cdc5397aef1741961c11a0c96b910546cd8f9d28`。GLM-5.3-flash、enabled/low、流式、输出上限 4,096。每题 30 分钟、96 次工具、128 次转发、请求超时 90 秒、5 USD 控制预算，整轮 10 USD；官方 Agent 时限是三小时，本轮是受限试跑。

包装器显式配置总窗口 **216,000**，扣除输出 4,096 和安全余量 4,096后，输入预算 **207,808**，自动压缩触发值为 **166,246** 个本地估算 Token。两题最高估算分别为 **118,096、42,284**，没有请求因上下文或字节保护被拦截，摘要请求都是 **0**。

因此，本轮能够说明任务继续执行并产生了代码；没有验证完整 216k 请求是否被服务商支持，也没有验证自动摘要质量、垃圾回收触发效果或摘要的真实 Token 收益。

ContextOS 仍在工作：较旧工具内容会被投影为引用。它的目标仍是 **32,000 字节**，与模型 Token 窗口是两个独立配置。请求字节投影统计不等同于 provider Token 节省，未作为计费收益发布。

## 评测包装器的问题与处理

### 1. 空输出处理失败：发生在模型调用前

首次 v3 启动把空 Git 状态输出当作字符串处理，Pier 实际返回 `None`。该启动记录保留，**模型请求 0、费用 0**。v3b 修正空值处理，并在付费前让离线预检执行实际仓库准备函数。

### 2. Git 权限合同仍不完整

可信准备步骤核对干净的任务源码基点，从 `main` 创建分支，设置仓库本地身份和 `.tea` 忽略规则；自动审批器增加受限 Git 操作权限。题目要求的新分支已存在。

但 `git checkout -b NAME main` 这种显式指定起点的常用形式仍被自动审批器拒绝；Helm 实际遇到两次。复合命令、`run_tests` 中不支持的 Git 参数也导致失败。生产命令正则在离线预检中还误拦了 `git log --format=...`。

自动策略拒绝会被反馈成“用户拒绝”，这不能理解为用户没有授权本轮测试。模型缺少准确的能力说明，容易选择错误工具或重复尝试。付费开始后未临时放宽权限，残留限制写入实验记录。

Go 在 TEA 精简的子进程环境下直接运行测试会缺少缓存目录；预检确认显式指定临时缓存目录可以运行。该入口被允许，但未注入提示或执行 shim，Helm 本轮没有运行到有效测试。

### 3. 原补丁导出失败：不能算作官方验收失败

模型结束后的可信收尾使用 `git add -A -- . ':!.tea'`；当 `.tea` 已被本地忽略时，这一写法返回 1，导致两条原始 Trial 都未进入官方验证。离线自编 fixture 重现了问题，并验证普通 `git add -A -- .` 能忽略私有状态、正常提交和导出。

为避免重新付费执行编码，使用原记录恢复待验收产物：

- 从相同任务基点启动干净容器；
- 用相同版本的生产 `WorkspaceTools` 重放原先成功的创建与补丁操作，逐项核对工具返回值与改动文件列表；
- Helm 重放 6 项，mnamer 重放 11 项；mnamer 另外核对最终只读工作区备份中改动文件的 SHA-256；
- 使用修正后的可信 staging 和带 DCO 签名的提交交给官方收集器，再在独立容器验证。

**没有新增模型请求，没有修改候选解法，没有把官方反馈送回模型重试。** Helm 没有最终工作区备份，只能凭固定基点与完整成功操作做确定性重建，不能声称与原先未能导出的补丁做过直接哈希对比。两题的原始异常和失败记录均保留。

这次预检遗漏完整导出生命周期，是评测实现的问题；不能因为单项命令预检通过，就假定完整评测流程可用。

## Agent 轨迹暴露的问题

### 检索没有及时转化为实现

Helm 的首次成功编辑出现在**第 80 次工具调用**。全程 42 次读取、28 次搜索、12 次召回和 2 次列目录，共 84/96 次；只做了 1 次创建和 5 次补丁。18 次读取/搜索/召回与先前调用参数完全相同。最终没有有效验证机会。

这说明工具次数分配存在问题。扩容延长了可执行轨迹，但不能自动保证模型推进任务。不能据此断言所有重复读取都无用，或把全部额外 Token 都归因于 ContextOS。

### 自测通过未覆盖完整需求

mnamer 第 9 次工具调用就开始成功编辑，进行了 5 次被 TEA 记录的有效验证尝试，最终验证状态通过。但官方新增功能仍有四项失败。官方 CTRF 名称指向日志/状态子目录和启动、重启生命周期；Helm 的失败项指向 upgrade dry-run 的确定性渲染排序。

这些是官方反馈中的失败类别，不是已定位到源码行的因果结论。已有行为全部保留，也不能弥补新功能缺失。Python 没有耗尽工具额度，因此不能把两题失败都解释为预算不足。

### 证据预算与窗口配置缺少联动

扩大 Token 窗口并没有扩大 ContextOS 的 32 KB 证据目标。可能需要更稳定的当前工作文件集合、连续代码页和回收策略，以减少刚逐出又召回的内容。

这里只提出机制假设。未做相同审批合同下的 ContextOS 开关、目标大小和工作集策略对照，不能声称它已经是重复检索的确定原因。

## 下一步顺序

1. **先补齐评测生命周期预检**：覆盖真实分支语法、自动策略拒绝原因、忽略状态存在时的提交、补丁收集和独立验证；生产验证入口与 Go 缓存环境另作明确实现和回归。
2. **再改任务推进策略**：根据公开需求建立功能与验证清单；持续重复检索且没有新证据时提示选择编辑、验证或报告缺少的能力。避免强迫所有任务在固定少量读取后盲目改代码。
3. **单独实验 ContextOS 工作集策略**：窗口与证据目标协调，优先保留正在编辑的相关文件和连续代码；同时测量总请求次数、真实 Token 与完整验收，不能只看单次请求变小。
4. **强化需求覆盖验证**：从公开题目识别多入口、路径、启动/停止/重启等边界，不把一次局部测试通过当作整题完成。不把本次隐藏反馈的具体测试名写进通用提示词。
5. **做可比较的下一轮**：固定同一合规审批合同后再单变量比较。原两题已经看过验证反馈，后续仅作回归；增加预先选定的未见任务，保留失败、未知和全部用量。

本次仅继续测试并记录结果，未改生产源码、未重新启用已回退的摘要预算/恢复候选，也未开始下一轮付费优化。
