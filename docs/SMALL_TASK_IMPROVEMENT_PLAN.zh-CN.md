# TEA 小任务 Token 改进计划

[English](SMALL_TASK_IMPROVEMENT_PLAN.md)

制定日期：2026-10-12。状态：S0、S1 已完成；S1 默认关闭并等待审核，S2–S5 尚未实施。[S1 真实对照](../benchmarks/reports/small-task-s1-glm-20261012/README.zh-CN.md)、[S0 零付费实施报告](../benchmarks/reports/small-task-s0-20261012/README.zh-CN.md)。

## 目标与基线

- 目标：在代码正确、任务要求和原生流程完成度不下降的前提下，减少额外模型请求，尤其是补充验证受阻后的重复操作。
- 起始基线：`97e8d5bdcd7e8e339247ad5ffb659bbb9c7683d9`。此前付费默认额度实验冻结引擎为 `b37322f`，后续提交只有报告和绘图变化；两个来源分别记录。
- 小任务历史观察：TEA/Pi 为 155,754/102,293 Token，79/46 次请求；21 次 Shell 拒绝，20 次在公开测试通过后发生。最坏配对贡献净超额的 90.63%。[完整诊断](../benchmarks/reports/contextos-c-vs-pi-small-diagnosis-20261012/README.zh-CN.md)。
- 历史 52.26% 差额只用于选问题，不当作新候选的配对基线。每个候选必须重新运行其直接父版本；旧失败、费用和验收记录保留。
- 首轮优化目标设为：小任务全部尝试的实际 Token 相对父版本减少至少 **10%**，并明显减少重复能力拒绝。这是实验目标，**不是预期收益或承诺**。

## 执行顺序

S0 评测与记录 → S1 能力说明和错误反馈 → S2 结构化补充验证 → S3 进度与结束判断 → S4 版本化补丁反馈 → S5 泛化与整体确认。

每项分别开发、冻结和测量。上一项未通过则回退该项，保留记录，重新判断下一项是否仍有价值。已通过的项可以成为下一项父版本；最终还需与起始基线做整体对照。

## S0：先让评测能准确区分问题

**改动内容**

- 支持在同一个外部对比脚本中加载指定的基线和候选 Git 提交；源码分别冻结，使用相同网关、模型控制、初始文件和验收版本。S0 已补齐双提交入口，支持具有当前原生会话 API 的 TEA 提交。
- 原生工具记录保存执行类别、经脱敏的程序/参数信息、命令哈希、批准结果、退出状态、完成时间、对应源码版本；完整敏感内容仍只在本地加密日志中。
- 将验收拆为：独立代码正确、修改范围、用户要求完成、修改后原生验证、原生正常结束、用量完整。公开测试通过不能替代全部目标验证。
- 修正过窄的测试命令识别：覆盖相对路径、带空格路径、参数顺序及实际测试脚本；结合工具完成事件和正向测试证据。无法确定时标为未确认，不用退出码或命令文本单独推断通过。
- 当前实验的完成见证和只读完整读取要求继续保留；新规则形成新验收版本，先冻结再对双方运行，旧结果不重算。
- 在调整提示或代码前固定 S5 的独立任务清单，避免后来按候选表现挑任务；识别各语言实际可用的运行环境。

**主要位置**：[对比脚本](../scripts/compare-contextos-pi.mjs)、[工具审计](../src/comparison-turn-audit.mjs)、[汇总](../src/comparison-report.mjs)、[独立验收](../src/contextos-benchmark.mjs)。

**验证与交付**

- 本地覆盖成功、非零退出、零测试、提前退出、测试未执行、修改后未重测、部分读取和未知用量。
- 真实 TEA/Pi 客户端的本地脚本合约检查；脚本化 Token 只作协议证据。
- 交付固定任务清单、配置、两个源码身份、验收版本和零付费预检报告。此阶段不宣称 Token 优化。

**S0 已验证**：254/254 完整测试；已提交父版/实现版的 18/18 本地合约任务；两套原生 TEA/Pi 合约；5 个真实仓库、20/20 故障任务预检。等价命令构造检查确认率 0/18 → 18/18，提升 100 个百分点；不是 Token 收益。准备 60+42 次后续配置，实际执行付费 Agent 运行 0 次。[冻结任务清单](../benchmarks/holdouts/small-task-v1.json)。

## S1：准确公布能力，给出可执行的错误反馈

**已完成并等待审核**：候选 `efaca4129ae2ea1fe58510749ada7464439daff7` 对父版 `c97b950`，267/267 测试；60 次小任务＋42 次保护运行，1,062 次请求用量全部已知。小/中/大型 Token 分别减少 41.44% / 37.11% / 4.53%，长会话增加 3.67%，全部矩阵减少 11.38%；候选完整验收 51/51，父版 47/51，独立代码正确 51/51 对 50/51。通过已定规模分组门槛，保留可选开关 `TEA_CAPABILITY_FEEDBACK=1`，默认关闭；11/30 小任务配对增耗，大型重试子组增加 5.19%，不保证每任务受益。验收差异中的保守验证失效规则单列解释，不重写原记录。[完整结果、负向样本与图表](../benchmarks/reports/small-task-s1-glm-20261012/README.zh-CN.md)。

**假设**：模型知道某类执行不可用，并得到明确替代方法后，会减少改写同一种被拒命令。

**改动内容**

- 会话开始时固定公布平台、验证入口、相对路径规则、交互批准是否可用；能力变化有独立版本号，避免每轮任意改变工具定义。
- 给失败返回稳定类别、`retryable`、缺少的能力和允许的下一步。区分能力拒绝、批准不可用、输入错误、当前源码不匹配、测试失败和临时运行故障。
- 这一项只调整说明与反馈，保持原执行权限和循环停止逻辑，以便单独判断收益。
- 反馈必须适用于工具类别和平台，不匹配 `truncateText`、重试函数名或固定任务用语。

**主要位置**：[工具定义与错误](../src/tools.mjs)、[提示和工具结果处理](../src/agent.mjs)、[持久化](../src/session-memory.mjs)。可按需拆出独立能力/错误模块。

**验证与交付**

- 覆盖交互、无交互、用户拒绝、会话恢复、平台变化和无效路径；保持原工具消息配对、签名、费用与错误状态。
- 新反馈不能把“不能执行”变成“验证成功”。
- 按下述固定矩阵测父版本/候选；未过质量与 Token 门槛则回退说明改动，转入其他单项。

## S2：提供可用的结构化补充验证

**假设**：经批准的验证能够直接执行后，可减少字符串引用失败和缺少边界证据引起的额外请求。

**改动内容**

- 设计 `program/args/stdin` 形式的验证入口。现有底层已经采用 `shell:false`；改进重点是上层命令字符串过滤、参数解析和能力协商。
- 批准绑定程序、完整参数、工作目录和脚本内容哈希。批准测试入口不等于批准任意内联代码；无交互且无预授权时准确报告不可用。
- 采用可信程序路径、工作区内的目录、现有脱敏环境、超时和进程树中断；单独处理 Windows npm 启动需求。结构化参数不提供操作系统隔离。[Node 官方进程文档](https://github.com/nodejs/node/blob/v24.14.0/doc/api/child_process.md)。
- 兼容原命令接口，优先可移植的测试入口；临时验证不得偷偷修改用户要求保留的测试文件或扩大修复范围。
- 若实验需要新增预授权验证能力，必须对基线与候选提供相同的批准策略，单列配置；原生 Pi 的权限差异继续披露。

**主要位置**：[执行与派发](../src/tools.mjs)、[批准与运行状态](../src/agent.mjs)、[配置](../src/config.mjs)、对比脚本。

**验证与交付**

- Windows/Ubuntu、Node 20/22/24；引号、分号、箭头函数、空格路径、UTF-8、多行 stdin、错误退出、超时与中断。
- 覆盖越界目录、错误程序、未批准参数/脚本和批准后内容变化。不得通过取消原权限检查换取收益。
- 先验证同一权限配置下是否改善；权限变化只作为单独的能力敏感性结果。

## S3：检测无进展循环，正确判断完成

**假设**：区分执行能力失败与代码失败后，可以避免重复拒绝诱发无依据的源码修改。

**改动内容**

- 能力拒绝按“能力类别＋批准版本＋环境版本”归组；修改源码不能重置一个仍不可用的执行能力。
- 测试失败、补丁冲突按“验证/操作目标＋当前源码版本”归组；真实修复、更新读取或新测试证据可开启必要的下一次尝试。
- 初始实验参数：同一能力拒绝两次后只给一次明确的替代路径提示；后续仍无能力或验证进展时，进入受限/未完成状态。参数在付费前固定，不能挑结果调阈值。
- 给需求、验证范围和版本记录来源；模型推断与实际测试证据分开。单条公开测试变绿不能直接结束任务。
- 测试通过后，只有仍有要求或新的问题证据才继续改代码；能力被拒不是代码失败证据。关键验证不可完成时明确报告限制，不虚报成功。
- 真实测试失败、跨文件任务、新用户要求、外部源码变更和已批准能力恢复必须能继续工作。

**主要位置**：[主循环与验证状态](../src/agent.mjs)、[恢复状态](../src/session-memory.mjs)、[任务状态呈现](../src/context-assembler.mjs)。

**验证与交付**

- 回放最坏 Unicode 行为链，以及合理的多轮修复、临时故障和任务切换；证明减少重复尝试不会截断有效修复。
- 新增日志记录“为何继续/为何受限”，但不引入额外付费模型做停止判断。
- 即使 Token 大幅下降，只要因为少做必要工作而完成率下降，本项也不能通过。

## S4：提供当前版本补丁回执与路径反馈

**假设**：短而明确的当前源码反馈能减少读错版本、补丁搜索失败和额外重读。

**改动内容**

- 补丁结果返回路径、前后哈希、实际改动范围、是否改变内容和少量当前片段；片段有大小上限，不能重新输出整个大文件。
- 搜索失败明确要求读取目标文件的新版本；回执进入来源追踪，旧副本不能成为当前证据。
- 明确相对路径；如支持工作区内部绝对路径，安全规范化后继续使用相对标识，阻止工作区外和符号链接越界。
- 无变化补丁保留有效验证状态属于防御性修复；历史最坏例没有这种补丁，不将它当作已发现原因。

**主要位置**：[补丁和读取](../src/tools.mjs)、[验证失效](../src/agent.mjs)、[版本依赖](../src/context-assembler.mjs)、会话恢复。

**验证与交付**

- 唯一/缺失/歧义匹配、相同内容、外部变化、大小写路径、空格路径、UTF-8 和恢复后的版本一致性。
- 单独计算新增回执 Token 与减少请求的净效果。返回内容更丰富本身不能当作收益。

## S5：泛化、整体确认与交付

- 使用 S0 固定的至少 20 个未用于设计的独立任务，来自至少 5 个真实开源仓库、每仓库最多 4 个任务，覆盖多文件修改、JS/TS、Python 和另一种可运行语言；每任务三重复、父版/候选两侧，共 120 次运行。
- 仓库与任务在试验前固定提交、授权来源和验收。目标复杂度必须有变化，不能只增加无关文件。
- 加入没有能力拒绝的简单任务、必须额外验证的任务、合理失败重试、跨文件任务、恢复后源码改变和实际长会话。
- 保留独立验收。正式保密留出评价需要隔离验收控制器和凭据；当前无 OS 隔离的自编样本只作诊断证据。
- 单项通过后，以起始基线/最终组合重新做同条件对照，并单列关闭每项的消融检查；不靠拼接各阶段最佳结果计算整体收益。
- 最后再跑原生 Pi 参考。不能把 TEA 与 Pi 的原生权限差异解释为记忆收益，也不混合不同额度或验收版本。

## 每个候选的固定实验矩阵

**先做零 API 检查**：相关回归、消息协议、恢复和预算，覆盖默认完整历史、ContextOS 与已有会话压缩的兼容；全套确定性测试与六项 CI。S0 的新增评测检查已执行，S1–S5 的专项测试随各阶段实现。默认完整历史的付费确认另立配置，不拼入以下 ContextOS 矩阵。

**第一批，小任务**：3 个原任务配置 × 10 次重复 × 父版本/候选 = **60 次运行、30 组配对**。三类全选，不只重跑失败项。

**通过后，保护性对照**：6 个中大型原任务配置 × 3 次 × 两侧 = **36 次**；实际空会话 30 次完整读取再修复 × 3 次 × 两侧 = **6 次**。每候选完整确认为 **102 次、51 组**。长会话两侧都采用 24 次工具额度；旧 10 次额度结果不拼入。

**进一步确认**：通过 S5 的 120 次未见任务对照，再做最终 Pi 参考；未完成时仅报告已完成阶段，不能宣布泛化门槛通过。

共同固定 GLM-5.3-flash、enabled/low、4,096 输出、160,000 UTF-8 字节输入保护、每轮 24 次工具、每运行 100 次请求、90 秒请求超时、180 秒单轮超时。ContextOS 两侧均主动开启、目标 32,000 字节、模型摘要关闭。每个任务配置使用相同初始 Git 内容，交替顺序，保留原生缓存与全部失败。

首个候选总费用上限暂定 **USD 8**、每运行上限 **USD 1.40**；预算费率取已核对的实际分组配置，预算估算不当作账单。后续批次按已知用量先固定各自有限总上限再启动。未知用量保留完整预留并停止付费；预算中止保存全部数据，全体比例不得用不完整组计算。本计划不启动这些付费调用。

## 通过、继续实验与淘汰规则

1. **质量先通过**：代码、范围、用户要求、原生验证与完成分别报告。总体及每个保护组的完成数不得下降；任何新增越界、漏做必需验证或虚报完成直接淘汰。
2. **配对失败逐例处理**：父版通过/候选失败不能被其他样本的提升抵消解释。先调查，若要确认则事先固定整组复验；不只重跑失败例、挑最好一轮。
3. **Token 门槛**：小任务全体实际 Token 相对直接父版下降至少 10%；全体计入缓存读写、思考、工具重试及失败。未达到则保留实验结果，不转为默认优化。
4. **其他任务保护**：中大型和长会话全体 Token 不得增加超过 5%；超过就淘汰或拆分成明确条件的可选策略，再独立重测。
5. **时间保护**：相同运行条件下 P95 耗时增长超过 10% 不通过性能门槛；报告中位数和 P95，不从 Token 降幅推导速度。
6. **统计限制**：报告每配对、每任务家族、全体和双方通过子集；确认时按独立任务聚类计算配对自助法 95% 区间，避免把同一任务的重复当成独立项目。区间不足以支持改善时标“收益未确认”，候选继续保持可选。
7. **失败处置**：回退本项运行时改动，保存失败记录和费用；选择下一项有证据支持的方向。单纯降低思考、压缩短会话、增加额度均不作为优先替代方案。
